### P2/P3 sequence and version qualification

P2a defines interfaces without a database dependency. P2b implements those contracts in isolated local PostgreSQL with synthetic identities only. P3a integrates verified identity with that same current-membership repository. P3b migrates remaining repositories after authorization is established. There is no circular dependency and no temporary production membership authority.

PostgreSQL 18 is a candidate, not a pinned requirement: local psql 18.6 is installed, while no psycopg/SQLAlchemy/Alembic application dependency exists. Before pinning, verify the approved managed provider version/extension/backup support, Python 3.12 driver versions, transaction/pool behavior and migration tool compatibility using official support matrices and isolated integration tests. No paid hosting selected by this plan. Prefer existing FastAPI deployment on managed containers with bounded solver workers; compare a single managed service initially against separate workers plus queue only after P5 measurements. Firestore is not an alternative authoritative schedule database.

Academic pilot rules retain Asia/Manila, semesters with midterm/final phases and effective-date exceptions. Existing 180 weekly minutes with 180-once or 90-twice patterns are configurable scenario rules, not verified institutional policy. Faculty workloads, Saturday/lab rules, transition buffers, locked assignments, room suitability and approval authority require explicit institutional decisions; incomplete scope is never school-wide readiness.

## Future publication unit of work (P7, not P1)

**Owner:** Scheduling service `PublicationCoordinator`, over a single authoritative PostgreSQL database transaction. Academic does not approve/publish through a separate HTTP transaction. Token cryptographic verification occurs before transaction; current membership and approval authorization are checked inside it.

Use SERIALIZABLE plus a common write protocol: tenant/dataset guard row → current actor membership → idempotency record → sorted academic period/revision rows → sorted publication heads → sorted candidate/approval rows. Shared resources across periods participate under the same tenant/dataset guard. All academic/resource/enrollment/membership writers acquire this guard before DML and bump relevant revisions in the same transaction. This intentionally conservative per-tenant serialization is a pilot correctness choice, to benchmark before relaxing.

Within that transaction: confirm tenant membership/approved policy; compare expected head, academic revision, approval and immutable payload hash; independently validate against current active scope; insert immutable publication/projection metadata, update active head, append audit and outbox; commit once. No network/Firestore/SSE delivery inside transaction. Snapshot-only enrollment is insufficient: every personal read must check current enrollment and membership, including irregular cross-section enrollment.

Migration owner is non-login. Runtime roles have no superuser/BYPASSRLS or schema-alter privilege. Academic writers get controlled mutation functions; Scheduling publication role gets SELECT of authorized inputs and narrowly scoped publication function/INSERT permissions, not arbitrary academic DML or UPDATE/DELETE of immutable publication rows. Notifications can claim/update delivery outbox only. Composite tenant FKs and FORCE RLS reinforce application checks; transaction-local tenant/actor context must reset on pooled connections. Function ownership/search_path/grants and absence of direct bypass grants need security tests before release.

Retry SQLSTATE 40001/40P01 up to three total attempts with bounded jitter; repeat all current authorization/revision checks. Stale business revision returns 409, not automatic approval of changed inputs. Exhaustion is a retryable error with no success claim. Duplicate exact idempotency request returns committed result; reusing a key with different payload rejects. Concurrent distinct publishes from the same expected head yield one commit, one stale rejection.

If an academic edit/enrollment removal commits first, publication sees a changed revision and rejects. If publication serializes first, retain its valid historical version; subsequent removal immediately affects access/projections, never silently rewrites history. Membership revocation first denies publish; publication first remains audited as authorized at its serialization point and all subsequent operations are denied. Test these outcomes with two real DB connections.

External side effects use a committed outbox, at-least-once delivery with event/version IDs and idempotent consumers. Crashes after commit resume delivery; duplicate/out-of-order events trigger version-aware authoritative refetch, never an overwrite from event payload. Notification outage does not undo committed publication. Recovery includes backlog reconciliation, not an exactly-once promise. Future supersession is a new version.

Emulator tests: cross-tenant/user reads, forged writes, revoked identity, duplicate/out-of-order event, expiry, disconnect/reconnect and outbox replay.
